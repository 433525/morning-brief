# 第 33 轮：让这份报纸开始处理「时间」与「错」 —— 更正栏 / 跨源矛盾检测 / 线索时间轴 / 落选公开

> 前两轮做的是「这份报能做什么」（第 31 轮视觉与形象、第 32 轮判断力与骨头）。
> 这一轮换了个问题：**一份报纸凭什么被信任。**
> 不是「我保证是真的」，而是敢说「我上次说错了」「这两个数字对不上，我不替你选」「这条我上次听到时还只是传闻」。

---

## 〇、出发点：三条洞察

写代码之前先把问题想清楚了，这一轮的每一件都从这三条长出来。

### 1. 所有人都在优化「发布那一刻」，而新闻的难点在「发布之后」

打开任何同类产品都是同一个动作：抓取 → 总结 → 呈现，回答「现在发生了什么」。

但新闻真实的形态是**会变形**的：

```
x.com 一条爆料  →  两家外媒跟进  →  官方确认但改了口径  →  一周后有人指出数据有误
```

第 33 轮之前，这份晨报每一期都在拍**快照** —— 它不知道「今天这条，昨天还是传闻」。
把新闻当快照做，它永远是聚合器；当**演化中的对象**做，它才是新闻产品。

### 2. 可信度的最高形式不是「我保证是真的」，是「我主动告诉你我哪里不确定」

同类产品的输出全是同一个语气：**确定的**。总结得越流畅，读者越不会怀疑。
但真正的编辑说的是「这条只有一家在报，先记着」「这两家数字对不上」。

**AI 新闻产品最缺的不是准确性，是承认不确定的能力** —— 而这句话技术上极易实现。

### 3. 新闻业需要的不是「生成」，是「可审计」

记者和编辑这个职业存在的很大一部分理由，是**流程可追溯**：一条稿子怎么来的、谁拍板的、依据是什么。
出事要能倒推。

而现在的 AI 新闻产品全是**黑盒**：214 条怎么被淘汰的、三个编辑各自说了什么、主编为什么选这条 —— 全部消失。
这一轮先把「本报自己说过什么」变成可查的台账（`read_ledger`），"过程可回放" 留到第 34 轮。

## 一、做了什么

### 1. 更正栏（Corrections）—— 这份报第一次会认错

这是整轮里最重要的一件。它现在会押注（第 31 轮）、会拒刊（第 32 轮），**但一直不会认错**。

**怎么做的：**

- **出报时**：主编在生成预测的同一次调用里，顺路把这一期报到的 3–5 条**硬事实**记进 `claims.json`
  （要求"尽量带上具体数字、公司名或版本号"，并且**只写本期标题里确实看到的，不许推测**）
- **下一期取数后**：`fact_kick()` 把上一期的台账和今天的新标题逐一比对，
  只有**今天出现明确证据推翻它**的才算一条更正
- **登在结果页最上方**（在预测卡之前 —— 报错了就写在最前面），并累计进 `fixlog.json`

**关键约束写进了提示词**：

> 今天没有消息、只是没被提到、或者略有出入但算不上推翻，一律不算，不要输出。

没有这一句，模型会倾向于"每条都能找到点毛病"，更正栏就会变成噪声。

### 2. 跨源矛盾检测 —— 拒绝综合，就是不制造确定性

比"跨期认错"更常见的问题在**同期**：同一天两家报同一件事，数字对不上。

- 把当天全部候选（带信源等级）摆在一起互校
- 找到「两条讲同一件事、关键数字或说法打架」的一对 → 出「**本报注意到口径不一致**」卡
- 两边原话并排摆着，标上各自的信源等级，主编写一句：**「两个数字都在，我不替你选。」**

**为什么这一条值钱**：几乎所有产品在这个位置都会选择「综合一下」，给出一个看起来更完整的说法。
拒绝综合 = 不编造确定性。这是产品立场，不是功能。

同时加了防噪声的约束：**"不要为了有东西而硬凑"**，没有就返回空数组。

### 3. 线索时间轴 —— 它开始记得一条消息的形状会变

- 归档时给每条新闻记一个 `stage`：**爆料 / 跟进中 / 已确认**
- 映射规则刻意做成**由信源成色推导**，而不是让模型去判断事件本身的阶段：
  - 一手来源（官方博客/仓库/论文）→ `confirm` 已确认
  - 二手（媒体报道）→ `follow` 跟进中
  - 传闻 / 转载 → `lead` 爆料
- 出报时拿本期入选条目跟本报档案里**同主题的上一条**比较阶段，变了就记一笔

界面文案：

> 「…… 本报听到它时还只是「爆料」，今天到了「已确认」」
> 「…… 本报手上是「已确认」，今天只有「爆料」级渠道在说」

**纯本地、零 LLM 调用**。而且因为 stage 说的是"本报这次是从什么成色的渠道听到的"，
而不是"这件事本身处于什么阶段"，它不构成对事实的越权判断 —— 这个措辞边界很重要。

### 4. 落选公开 —— 取舍被看见，才能被反驳

第 32 轮公开了淘汰率（扔了多少），但没公开**扔的是什么**。

现在主编在终审时要额外给出「最可惜的三条」及每条一句为什么没上（信源太薄 / 话题与已选重复 / 体量太小），
列在新闻列表之后。

**零额外成本** —— 加在 judge 已有的那次调用的输出 schema 里（`drops` 字段）。

### 5. 工具层 19 → 20

新增 `read_ledger`：查本报自己的更正与口径核对台账。读者问「你上次是不是报错了」时用它。

`ag_context()` 现在会把今天的口径核对结果、要登的更正、砍掉的三条、线索进展、累计更正数一并讲给主编。

## 二、技术上的四个决定

### 1. 为什么把「同期矛盾」和「跨期更正」合并成**一次**调用

看起来是两件事，本质是同一件：**把两批文本摆在一起，找出对不上的地方。**
区别只是两批文本是"今天 vs 今天"还是"上一期 vs 今天"。

合并之后，出报后只多**一次** LLM 调用（第 31 轮的预测、第 32 轮的拒刊都不增）。
在黑客松的语境下，这个成本差是会被注意到的。

### 2. 序号回指用**计数匹配**，不直接当索引

`fact_kick()` 和 `drops_from_ai()` 都要处理"模型返回的序号 → 本地列表下标"。
直接 `cand[iv]` 有风险：如果宿主把 JSON 里的 integer 返回成字符串，就是运行时崩溃。

所以统一走 `idx_in()`：

```
fn idx_in(v, list, n){
    let out = -1
    let i = 0
    for z in list {
        if z != nil {
            if i < n { if v != nil { if v == i { out = i } } }
        }
        i = i + 1
    }
    out
}
```

匹配不上就返回 -1（这一条被安静地忽略），而不是崩掉整个界面。
这个手法沿用自既有的 `fc_review()` —— 那一处是上一轮验证过的写法。

### 3. 顺序陷阱：`th_scan()` 必须在 `arc_add()` **之前**调用

`finish()` 里原本只有 `arc_add(picked)`。线索扫描要跟"档案里的历史"比，
如果先 `arc_add`，**本期条目会把自己当成上一条**，比对结果永远是"没有变化"，线索卡永远不出现。

```splash
last_at = finished_at
// 先拿这一期跟档案比阶段，再把自己写进档案 —— 顺序不能反
th_scan(picked)
arc_add(picked)
```

### 4. 两处「零额外成本」的扩展

这一轮的 4 个功能里，只有 1 个新增了 LLM 调用：

| 功能 | 落地方式 | 额外调用 |
| --- | --- | --- |
| 更正栏（抽断言） | 并进 `fc_kick` 已有的预测调用（schema 加 `claims`） | **0** |
| 落选公开 | 并进 `judge` 已有的终审调用（schema 加 `drops`） | **0** |
| 线索时间轴 | 纯本地推导（信源等级映射阶段） | **0** |
| 跨源矛盾 + 跨期更正 | 合并成一次 `brief.factcheck` | **1** |
